## Findings

## [medium] Merely watching a teammate's open agent types into it: terminal auto-replies are forwarded, and "Max typed" shows
- Where: app/renderer.js:1437 (`term.onData(d => ws.send({t:'in',...}))` on every watcher terminal), src/hub.js:610-618 (any `in` on an open lane is relayed and sets typedBy/typedAt)
- What happens: xterm.js answers terminal queries (cursor position `ESC[6n`, device attributes `ESC[c`) through `onData`. A watcher's terminal answers the same query the owner's own terminal already answered, so the agent's stdin gets each reply once per viewer, and David's lane shows "Max typed, just now" though Max typed nothing. With Claude Code / TUIs that probe the terminal this injects stray characters (`;1R1;2c...`) into the agent's prompt whenever someone looks at it.
- Evidence: CONFIRMED live (Duo, session checkout-flow, David's agent open=true, Max only watching, last real typing 18:31:56): David ran `printf '\033[6n\033[c'; sleep 1` in his agent. The shell got `^[[5;1R^[[?1;2c` twice (David's xterm + Max's xterm), left `;1R1;2c;1R1;2c` at the prompt, and David's `typedAt` moved from 18:31:56 to 18:32:34 with typedBy "Max". Before that, plain viewing (full size, then side by side) left typedBy "" (so it needs the agent to emit a query).
- Suggested fix: on watcher terminals drop input that is a terminal reply (CSI responses `\x1b[...R`, `\x1b[?...c`, focus `\x1b[I/O`), or only send `in` after a real keydown/paste in that pane; or let the hub ignore `in` from a watcher whose message matches those patterns.

## [low] Shell-write check asks about merely RUNNING a file a teammate changed, because of `2>&1`
- Where: src/hub.js:255-270 (`shellWriteRisk`: any `>` in the command, including `2>&1`, turns on the path scan; the "writes" are then any path-like word)
- What happens: `npx tsx src/match/queue.ts 2>&1 | tail` (run/test a file, merge stderr, tail) asks "Max already edited src/match/queue.ts, and this command changes it" though nothing is written. `cat src/match/queue.ts > /dev/null` does the same. `node x.js 2>&1 | tail` (file nobody changed) correctly stays silent. Agents append `2>&1 | tail` to almost every test/run, so on an overlapped file the agent gets a spurious ask on each run.
- Evidence: CONFIRMED live: POST /hook PreToolUse Bash on David's lane while Max's lane had changed src/match/queue.ts: Edit -> ask (correct); `sed -i '' ... src/match/queue.ts` -> ask (correct); `node x.js 2>&1 | tail` -> null (correct); `npx tsx src/match/queue.ts 2>&1 | tail` -> ask (false alarm).
- Suggested fix: strip fd redirects (`\d*>&\d+`, `\d*>\s*/dev/null`) before the `>` test, and for a `>` only consider the word after it as the written path.

## [low] Shell-write check misses directory-level deletes and git reverts of a file a teammate changed
- Where: src/hub.js:263-269 (`othersOn(lane, rel)` is an exact file match; `rel === ''` for the folder itself)
- What happens: with Max's change in src/match/queue.ts, `rm -rf <David's session folder>`, `rm -rf src` and `rm -rf src/match` return no ask (only `rm src/match/queue.ts` itself would), and neither does `git checkout -- src/match/queue.ts` (not in the write list at all; same for `git restore`, `git reset --hard`, `git stash`). The agent can wipe the file that the overlap warning is about without the coordinate-first ask.
- Evidence: CONFIRMED live via POST /hook (David's lane, cwd = session folder): all five answered `null`.
- Suggested fix: treat a path that is a directory prefix of an overlapped file (`f.startsWith(rel + '/')`, or rel === '') as a hit, and add `git (checkout|restore|reset|stash|clean)` to the write words.
