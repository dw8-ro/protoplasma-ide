## Release-job split (proposal from the build-ci reviewer)

RELEASE JOB SPLIT: a proposal only; no file was changed.

What the split protects, and what it doesn't: it keeps MAC_CERT_P12 and MAC_CERT_PASSWORD out of every process that runs dependency code (npm ci, the setup scripts, npm test, electron-packager), so a compromised dependency can no longer steal the signing key. It does not make the app itself trustworthy: a compromised build job can still put code into the unsigned app, and the sign job will sign it. Reproducible builds or a second, independent build would be needed for that. Taking the key out of reach is the large gain, because a stolen key could sign updates for every installed copy forever, and the certificate must never be replaced.

Outline (pin every action to a full commit SHA, with the tag in a comment):

```yaml
name: Release
on:
  push: { tags: ['v*'] }
  workflow_dispatch:
permissions: {}            # each job asks for its own

jobs:
  check:                   # runs no dependency code
    runs-on: ubuntu-latest
    permissions: { contents: read }
    outputs: { tag: ${{ steps.t.outputs.tag }} }
    steps:
      - uses: actions/checkout@<sha> # v5
        with: { fetch-depth: 0, persist-credentials: false }
      - run: git merge-base --is-ancestor "$GITHUB_SHA" origin/main
      - id: t
        run: |   # today's "Check the tag matches package.json" block, unchanged, ending with:
          echo "tag=$TAG" >> "$GITHUB_OUTPUT"

  build:                   # no secrets, read-only token, no npm cache
    needs: check
    runs-on: macos-latest
    permissions: { contents: read }
    steps:
      - uses: actions/checkout@<sha>
        with: { persist-credentials: false }
      - uses: actions/setup-node@<sha>
        with: { node-version: 24 }   # no `cache: npm`, so a main-branch cache can't be restored into a release
      - run: npm ci
      - run: npm run setup
      - run: npm test
      - run: npm run dist
      # upload-artifact drops symlinks and exec bits, and an Electron .app needs both
      # (Frameworks/*/Versions/Current, spawn-helper), so archive it first
      - run: ditto -c -k --keepParent dist.noindex/Protoplasma-darwin-arm64/Protoplasma.app unsigned.zip
      - uses: actions/upload-artifact@<sha> # v4
        with: { name: unsigned-app, path: unsigned.zip, retention-days: 1, if-no-files-found: error }

  sign-and-publish:        # installs nothing; the only job that sees the key
    needs: [check, build]
    runs-on: macos-latest
    environment: release   # required reviewer (David); deployment refs: v* tags and main
    permissions: { contents: write }
    env: { TAG: ${{ needs.check.outputs.tag }} }
    steps:
      - uses: actions/checkout@<sha>
        with:
          persist-credentials: false
          sparse-checkout: |
            scripts/sign.sh
            docs/release-notes
          sparse-checkout-cone-mode: false
      - uses: actions/download-artifact@<sha> # v4 (same run only)
        with: { name: unsigned-app }
      - name: Unpack and check what was built
        run: |
          mkdir out && ditto -x -k unsigned.zip out
          APP=out/Protoplasma.app; test -d "$APP" && test ! -L "$APP"
          P="$APP/Contents/Info.plist"
          [ "$(/usr/libexec/PlistBuddy -c 'Print :CFBundleIdentifier' "$P")" = com.electron.protoplasma ]
          [ "$(/usr/libexec/PlistBuddy -c 'Print :CFBundleShortVersionString' "$P")" = "${TAG#v}" ]
          test -x "$APP/Contents/Resources/app.asar.unpacked/node_modules/node-pty/prebuilds/darwin-arm64/spawn-helper"
      - name: Sign and zip
        env:
          MAC_CERT_P12: ${{ secrets.MAC_CERT_P12 }}
          MAC_CERT_PASSWORD: ${{ secrets.MAC_CERT_PASSWORD }}
        run: |
          scripts/sign.sh out/Protoplasma.app          # ends with codesign --verify --deep --strict
          ditto -c -k --keepParent out/Protoplasma.app "Protoplasma-${TAG#v}-mac-arm64.zip"   # name and layout unchanged
      - name: Publish
        env: { GH_TOKEN: ${{ github.token }} }
        run: |   # today's gh release create line, unchanged (gh is preinstalled on macOS runners)
          NOTES="docs/release-notes/${TAG#v}.md"
          gh release create "$TAG" Protoplasma-*-mac-arm64.zip --target "$GITHUB_SHA" --title "Protoplasma ${TAG#v}" --generate-notes ${NOTES:+$( [ -f "$NOTES" ] && echo "--notes-file $NOTES")}
```

What stays the same:

- The ad hoc refusal in CI: sign.sh exits 1 without the certificate.

## Findings in detail

### relay-main-1: Refuse-once lets a different step through when its hub reason text is the same (now covers OpenCode too)

- **Severity:** medium. **Verdict:** confirmed. **Also in 0.6.1:** yes. **Where:** `app/teams.js:186` (`refuseOnce`)
- **What:** refuseOnce records a refusal under the key `${laneId}|${reason}`, where reason is the hub's permissionDecisionReason. It does not key on the step itself. The hub's push reasons are generic. pushRiskOf returns 'this force-push can overwrite commits your teammates pushed. Confirm it's intended.' for every force push, and 'this pushes straight to <branch>...' for every push to a given shared branch. So once one step is refused, any other step with the same reason runs within 10 minutes without a refusal, and nobody has been asked about it. The comment, AGENTS.md:612 and README.md:167 all promise that only 'the same step' goes through. The branch extends this path from Codex to OpenCode (to.cmd && !AGENTS[to.cmd]?.asks). A related point: a hub that changes the reason each time (a counter, say) can make the refusal permanent. That contradicts 'a hub still can't refuse anything outright'.
- **Failure scenario:** A team has members. A Codex or OpenCode agent runs in a folder the person picked, where no pre-push guard is installed (startLane shows the not-guarded notice). (1) The agent runs `git push --force origin session/x`. The relay refuses it once. (2) Within 10 minutes the agent runs `git push --force origin main`. The hub gives the identical reason, so refuseOnce returns '' (no decision), and the force push to main runs without the person being asked. The same happens with a second, different push to main after the first was refused.
- **Evidence:** Reproduced with scratch script work/find-relay-main/f1.js: a fake hub answers 'ask' with the force-push reason, and the relay runs with cmd 'opencode'. The first hook (`git push --force origin session/x`) got permissionDecision 'deny'. The second hook (`git push --force origin main`) got an empty reply, so it is allowed. Code: teams.js refuseOnce, `key = `${id}|${reason}``; hub.js pushRiskOf, reason strings around lines 486 and 510.
- **Suggested fix:** Key the refusal on the step as well as the lane, for example a sha256 of the slim body's tool_name and tool_input (slimHook already produces it, so pass `slim` into refuseOnce). Optionally include the reason too. Add a lan.test.js case where two different commands get the same reason and both are refused once.
- **Skeptic:** The code at HEAD matches the report. refuseOnce (app/teams.js:182) records the refusal under `${id}|${reason}` and doesn't look at the step. The released 5e896c4 had the same logic as codexReply. The branch extends it from `to.cmd === 'codex'` to every agent without `asks`, which now includes OpenCode. The hub's reasons are generic. pushRiskOf (src/hub.js:487) checks for a force push before it checks the target, so every force push, including one to main, gets the same reason. Every push to a given shared branch also shares one reason. So after one step is refused, a different risky step with the same reason gets no refusal for 10 minutes, and the agent never gets the cue to ask. Conditions for this to happen: the team has members; a Codex or OpenCode agent runs in a folder the person picked, so no pre-push hook is installed (or the agent uses --no-verify); and two risky steps with the same reason come within 10 minutes. These are unusual conditions, and the outcome is a security weakening that can end in a push to main nobody was asked about. That makes medium right. It's partly inherent: an agent that ignores the refusal can already retry the identical step by design. The added gap is that a distinct step is never refused at all. The related point also holds: a hub that changes the reason every time can make the refusals permanent. That only blocks steps, so on its own it's low.
- **Skeptic's evidence:** I reran the reviewer's script as work/verify-relay-main/f1.js: a fake hub on 127.0.0.1 answers 'ask' with the force-push reason, and the relay runs with cmd 'opencode'. Hook 1 (`git push --force origin session/x`) came back with permissionDecision 'deny'. Hook 2 (`git push --force origin main`) came back with an empty reply, so it is allowed. teams.js:186 `key = `${id}|${reason}``; teams.js:253 `to.cmd && !AGENTS[to.cmd]?.asks ? refuseOnce(id, reply) : reply`; hub.js:486-487 is the force check that runs before the target check. On 5e896c4, teams.js codexReply has the same keying.
- **Skeptic on the fix:** Pass `slim` (it's already computed in hookRelay) into refuseOnce and key on `${id}|${sha256(slim)}|${reason}`. Keep the reason in the key: lan.test.js:201 ('another step is refused once too') posts the same '{}' body with a new reason, so keying on the step alone would break that test. Add a lan.test.js case where two different commands get the same reason and each is refused once. Update the comment at teams.js:175-178 to match.

### build-ci-1: npm run setup runs the install scripts of any package folder named node-pty or electron, including nested or npm-aliased ones that were never vetted

- **Severity:** medium. **Verdict:** confirmed. **Also in 0.6.1:** no. **Where:** `scripts/allowed-scripts.js:18` (`allowed-scripts.js loop / npm rebuild <name>`)
- **What:** The script checks the version only of the top-level node_modules/<name>/package.json, then runs `npm rebuild <name> --ignore-scripts=false`. npm's rebuild (lib/commands/rebuild.js isNode) picks every non-bundled node whose folder name equals <name>, at any version, because the spec has no version (rawSpec ''). So a nested copy at another version, or a transitive dependency aliased to that name (`"node-pty": "npm:evil-pkg@x"`), also gets its install scripts run. That is the exact thing .npmrc ignore-scripts=true is there to stop. npm 11.20's own allowScripts gate does not block it either, because an unlisted package counts as allowed.
